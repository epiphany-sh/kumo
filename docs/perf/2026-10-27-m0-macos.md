# M0 — macOS — 2026-10-27

- Máquina: Apple M2 Max, 12 núcleos lógicos
- SO: macOS 27.0.1 (26A434)
- Rust 1.99.1, build `--release` (LTO thin)
- Comando: `./target/release/kumo-bench all` (daemon con defaults: 2 workers)
- Ojo: máquina de desarrollo con carga de fondo (load avg ~6–12 al medir).

## Resultados

| Métrica (kumo.md §4) | Objetivo | Medido | |
|---|---|---|---|
| RTT `Hello` unary (n=10.000) | p99 ≤ 1 ms | p50 0,048 · p99 **0,071** · max 0,193 ms | ✅ |
| Eco de tecla vía gRPC, sin UI (n=1.000) | p50 ≤ 1 ms, p99 ≤ 3 ms | p50 **0,467** · p95 0,724 · p99 **0,868** · max 1,817 ms | ✅ |
| Tramo daemon (lectura PTY → cliente) | p99 ≤ 2 ms | p50 0,161 · p99 **0,339** · max 0,990 ms | ✅ |
| Throughput sostenido en el daemon | ≥ 50 MB/s | **107 MB/s** (`kumo-echo flood`, 100 MiB) | ✅ |
| Memoria del daemon en reposo | ≤ 50 MB | **3,5 MB** RSS | ✅ |

El "tramo daemon" se mide como `ahora − first_read_unix_nanos` al recibir el batch
en el cliente: incluye socket y decodificación, así que es una cota superior.

## Workloads de `kumo.md` limitados por el productor

| Workload | kumod | Mismo PTY sin daemon (`script -q /dev/null …`) |
|---|---|---|
| `seq 1 5000000` | 8,47 s (7,0 MB/s) | 8,34 s |
| `head -c 100M /dev/zero \| tr '\0' x` | 4,74 s (22,1 MB/s) | 4,58 s; `tr` solo, sin PTY: 4,72 s |

- `seq` escribe línea por línea a la tty (5M syscalls de `write`).
- `tr` de BSD procesa ~22 MB/s aunque escriba a `/dev/null`.
- En macOS cada `read()` del master devuelve como mucho 1 KiB; la cola de la tty
  no acumula más (verificado con `FIONREAD`), así que el pump no tiene qué coalescer.

Por eso el número de throughput del daemon se toma con `kumo-echo flood`
(bloques de 64 KiB). El overhead del daemon sobre el PTY pelado es ≤ 4 % en esos workloads.
